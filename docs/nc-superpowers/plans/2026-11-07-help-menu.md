# Help menu implementation plan

> For agentic workers: REQUIRED SUB-SKILL: Use nc-superpowers:subagent-driven-development or nc-superpowers:executing-plans to implement this plan in task order. Steps use checkboxes for tracking.

**Goal:** Give onesie a short help overview, focused topics and a complete reference, with one definition of each flag description and topic explanation.

**Architecture:** Keep flag facts and presentation metadata on the existing setting rows. Compose command specific views from registered flags and CLI owned topic content. Extend the existing help dispatcher and migrate the skill checker to complete help before enabling the shorter overview.

**Tech stack:** Go, the existing Cobra and pflag versions, existing CLI dependency injection, mock answers and golden help files. Add no dependencies.

**Spec:** `docs/nc-superpowers/specs/2026-11-07-help-menu-design.md`.

**Baseline:** `9751e55`, on `codex/help-menu-spec`. Runtime code is the v0.14.0 release. The spec is approved. This plan is for review, not authorization to implement or publish.

## Global constraints

- Preserve parsing, question binding, settings resolution, validation, defaults, output contracts and run exit codes.
- Topic names exist only beneath help. They must not become executable root commands or new reserved positional questions.
- Root has exactly fifteen common flags. Calibration has the fourteen common flags named in the spec.
- Every visible flag appears exactly once in its command complete reference, including inherited flags and Cobra owned help.
- The same command flag uses the same description, signature and default in every help view.
- All help works without credentials, profile reads, keychain access, stdin reads or network requests.
- Descriptions wrap to 88 columns. Preserve example lines. Use plain text with no terminal width dependency, color requirement or pager.
- Follow caller above callee ordering. Exported declarations have short doc comments. Unexported declarations have no doc comments.
- Test functions name the covered unit. Every test uses subtests whose names begin with `should `.
- Use only comma, period, exclamation and colon in English prose. Preserve identifiers, code syntax and Markdown syntax.
- Use signed semantic commits with one line and no attribution. If signing reports `failed to fill whole buffer`, stop and request that 1Password be unlocked. Never bypass signing.
- Standalone binary trials use an isolated environment and mock answers or a fake local endpoint. Never read real keys, `.env`, real profile directories or the real OS keychain.
- The user already approved an isolated environment for offline `make skills-check`, whose runner clears mock and endpoint variables before offline checks.
- This is one focused PR when execution is approved. Use one Sol implementer for the PR, then a separate Sol reviewer. Tasks below are sequential commit boundaries, not separate PRs.
- Use an isolated worktree at execution time. Do not implement in the planning checkout. Push, merge and release remain outside this plan execution unless separately authorized.
